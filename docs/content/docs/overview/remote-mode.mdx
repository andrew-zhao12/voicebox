## Overview

Remote Mode allows you to run the Voicebox backend on a separate machine (like a GPU server) while using the desktop app or the web UI on your local machine.

## Use Cases

- **No local GPU** - Use a cloud GPU or remote workstation
- **Faster generation** - Leverage powerful remote hardware
- **Shared infrastructure** - Multiple users connect to one server
- **Laptop workflows** - Keep your laptop cool and battery-efficient

## Architecture

In Remote Mode, the Voicebox desktop app (running on your local machine) communicates with the backend server (running on a remote machine) via HTTP. The local app provides only the user interface, while the remote server handles all the heavy processing including the TTS models, API endpoints, and audio generation.

Every request carries an [API key](/overview/api-keys). The server answers only callers that present one, so the key is what you hand to each client, whether that is the desktop app, the web UI, an agent, or your own code.

## Setting Up Remote Mode

### On the Server

<Steps>
  <Step title="Install Dependencies">
    ```bash
    # Clone the repo
    git clone https://github.com/jamiepine/voicebox.git
    cd voicebox/backend

    # Install Python dependencies
    pip install -r requirements.txt

    # Engines with incompatible transitive pins — install with --no-deps
    pip install --no-deps chatterbox-tts
    pip install --no-deps hume-tada

    # Qwen3-TTS from source
    pip install git+https://github.com/QwenLM/Qwen3-TTS.git
    ```

    Or just run `just setup` from the repo root, which handles all of this.
  </Step>

  <Step title="Choose an API Key">
    ```bash
    # Back to the repo root
    cd ..

    # A random admin key; you will enter it on every client
    export VOICEBOX_API_KEY="$(openssl rand -base64 32)"
    echo "$VOICEBOX_API_KEY"
    ```

    If you skip this, the server writes a key to `data/api_key` on first start and `python -m backend.keys local` prints it. Either way, keep the key somewhere safe.
  </Step>

  <Step title="Start the Server">
    ```bash
    # Run from the repo root; --host 0.0.0.0 allows external connections
    uvicorn backend.main:app --host 0.0.0.0 --port 17493
    ```

    <Callout type="warn">
      This exposes the server to your network. Callers need the API key, but plain HTTP shows that key to anyone on the path between client and server. Stay on a trusted LAN or VPN, or put HTTPS in front (see [Security Considerations](#security-considerations)).
    </Callout>
  </Step>

  <Step title="Open Firewall">
    ```bash
    # Ubuntu/Debian
    sudo ufw allow 17493

    # Or use your cloud provider's firewall settings
    ```
  </Step>
</Steps>

### On the Client

Every client asks for the same two things: the server URL and the API key.

**Web UI** (a [Docker](/overview/docker) install, or `just dev-web`) opens on a **Connect** screen:

<Steps>
  <Step title="Enter the Server URL">
    ```
    http://<server-ip>:17493
    ```

    Replace `<server-ip>` with your server's IP address, or use `https://<your-domain>` once TLS is in front of the server.
  </Step>

  <Step title="Paste the API Key">
    The field is masked like a password. The browser keeps the URL and key in its local storage until you disconnect from **Settings → General**.
  </Step>

  <Step title="Test, then Connect">
    **Test** shows the key's id and role as the server sees them. The UI needs an `admin` key; a `client` key is refused here. **Connect** loads the app.
  </Step>
</Steps>

**Desktop app**: go to **Settings → General**, set the server URL, paste the key into the API-key row next to it and click **Test**.

<Callout type="info">
  The desktop app reconnects to its bundled local server every time it launches, so a remote URL and key apply to the current session. Enter them again after a restart.
</Callout>

### Using the Desktop App as the Server

The desktop app can be the server for other devices. In **Settings → General**, turn on **Allow network access** and restart the app; the bundled server then listens on all interfaces instead of only `127.0.0.1`. Other devices connect with the app's own key, which you can copy from **Settings → MCP → Copy API key**. That key is an admin key travelling over plain HTTP, so keep this to a trusted network.

## Security Considerations

Every endpoint requires an API key, so nobody without one can use a server on the network. The key is the only secret, though, and plain HTTP reveals it to anyone on the path between client and server.

<Callout type="warn">
  Keys must only travel over loopback or HTTPS. Plain HTTP is fine on a trusted LAN or through a VPN; anything reachable from the internet needs TLS in front of the server.
</Callout>

**Best Practices:**
- Use a VPN (WireGuard, Tailscale) instead of exposing the port to the internet
- Terminate TLS in a reverse proxy. With Docker, the bundled Caddy overlay does it for you: `VOICEBOX_DOMAIN=voice.example.com docker compose -f docker-compose.yml -f docker-compose.tls.yml up -d` (see [Docker Deployment](/overview/docker#tls-with-caddy)). Basic auth is not needed; the API key already authenticates every request.
- Give each app or agent its own `client` key and keep the admin key for the UI (see [API Keys](/overview/api-keys)); revoke a key the moment it leaks
- Set `VOICEBOX_DISABLE_DOCS=1` on servers that don't need the interactive API docs
- Behind your own proxy, set `FORWARDED_ALLOW_IPS` to the proxy's address so per-IP rate limits see the real client, and never `*` on a published port
- Firewall rules to limit access to specific IPs

On a bare host, this Caddyfile is enough for automatic HTTPS in front of the server:

```
voice.example.com {
    reverse_proxy 127.0.0.1:17493 {
        flush_interval -1
    }
}
```

`flush_interval -1` keeps progress streams and streamed audio unbuffered. With any other proxy, disable response buffering for `/generate/stream` and the SSE routes the same way.

## Performance

Expected performance on various GPUs:

| GPU | Generation Speed |
|-----|------------------|
| RTX 4090 | ~2-3s per 10 words |
| RTX 3090 | ~3-4s per 10 words |
| RTX 3060 | ~5-7s per 10 words |
| CPU (12-core) | ~20-30s per 10 words |

<Callout type="info">
  A GPU with 8GB+ VRAM is recommended for best performance.
</Callout>
