This page is for operators putting the backend in front of applications, as a container on one host. It complements [Docker Deployment](/overview/docker) (how to run the container) and [API Keys](/overview/api-keys) (who may call what); [Scaling](/overview/scaling) continues with several replicas.

## 1. Pick an image variant

| Variant | Build arg | Wheels | When |
|---------|-----------|--------|------|
| `cpu` | `PYTORCH_VARIANT=cpu` (default) | PyTorch CPU build, about 4.5 GB image | Kokoro, LuxTTS, Chatterbox Turbo at usable speed; anything else is slow |
| `cu128` | `docker-compose.cuda.yml` | CUDA 12.8, torch 2.11, Blackwell included | NVIDIA GPUs with driver 570 or newer |
| `cu130` | `PYTORCH_VARIANT=cu130` with the CUDA overlay | CUDA 13.0, torch 2.14 | NVIDIA GPUs with driver 580 or newer |
| `rocm` | `docker-compose.rocm.yml` | ROCm 6.3 (7.2 for RDNA4) | AMD GPUs |

Prebuilt `-cpu` and `-cu128` images are published for every release tag (see [Prebuilt Images](/overview/docker#prebuilt-images)). Dependencies are pinned in `backend/requirements.lock`, so two builds of the same commit install the same versions.

## 2. Set the environment

```bash
export VOICEBOX_API_KEY="$(openssl rand -base64 32)"   # admin key; the UI and operators use it
export VOICEBOX_DISABLE_DOCS=1                          # no /docs on a server
export VOICEBOX_PRELOAD_MODELS=kokoro,whisper-turbo     # what /health/ready waits for
export VOICEBOX_RETENTION_DAYS=30                       # delete old generations and captures
```

Then give each application its own **client** key, which can synthesize, transcribe and read profiles but cannot change settings, delete data or download models:

```bash
docker compose exec voicebox python -m backend.keys create --id myapp --role client
```

The full variable list is in [Docker Deployment](/overview/docker#environment-variables).

## 3. Probes

| Probe | Path | Key | Meaning |
|-------|------|-----|---------|
| Liveness | `GET /health` | none | The process answers. Docker's `HEALTHCHECK` uses it. |
| Readiness | `GET /health/ready` | none | `200` once every model in `VOICEBOX_PRELOAD_MODELS` is resident and the queue worker runs; `503` while loading, after a load failed, or once the server is draining. |

Point load balancers and orchestrators at `/health/ready` so traffic only arrives once the first request can be served without a multi-minute model download. The body names the models that are still pending or failed; failed loads are retried every two minutes, and the reason is in the server log.

Kubernetes, for example:

```yaml
livenessProbe:
  httpGet: { path: /health, port: 17493 }
  periodSeconds: 30
readinessProbe:
  httpGet: { path: /health/ready, port: 17493 }
  periodSeconds: 5
  failureThreshold: 3
```

## 4. Warm-up

Models load on first use and stay resident. On a server, load them at boot instead:

- `VOICEBOX_PRELOAD_MODELS` takes registry names (`python -m backend.preload --list` prints them, for example `kokoro`, `qwen-tts-1.7B`, `chatterbox-turbo`, `whisper-turbo`). Each one is loaded as a job on the generation queue, so a generation that arrives during the warm-up simply waits behind it.
- To bake the weights into an image or an init container, run `python -m backend.preload kokoro whisper-turbo` (or `--from-env`) with the same `VOICEBOX_MODELS_DIR` / HuggingFace cache the server will use. It downloads and loads each model, then exits.
- Client keys cannot trigger downloads; a request for a model that is not on disk gets a `409`. Preloading avoids that.

## 5. Graceful stop

On `SIGTERM` the server stops accepting connections, finishes streams and SSE responses that are already open (up to 40 s), then drains its generation queue: new jobs are refused with `503` and `Retry-After`, `/health/ready` turns `503`, and queued and running generations get up to `VOICEBOX_DRAIN_TIMEOUT_S` (default 30) to finish before they are cancelled and the models unload. The compose file sets `stop_grace_period: 45s` to match; give your orchestrator a termination grace period of at least that.

Behind a load balancer, set `VOICEBOX_SHUTDOWN_DELAY_S` (10 is a good start): the first `SIGTERM` then only turns `/health/ready` to `503` while the server keeps accepting and serving requests for that many seconds, so the balancer stops routing to it before the listener closes and no request lands on a closing replica. A second signal skips the rest of the delay. Add the delay to the grace period (90 s covers 10 + 40 + 30). The default is 0, so the desktop app quits at once.

## 6. Retention

Generated audio and captures stay forever by default. With `VOICEBOX_RETENTION_DAYS=N`, a daily sweep deletes generations older than N days that are not favourited and not placed in a story, captures older than N days, and audio files that no database row references. `POST /maintenance/prune` (admin key; optional body `{"days": N}`) runs the same sweep on demand and returns what it removed. `0` keeps nothing older than today.

## 7. Observability

- **Request ids.** Every response carries `X-Request-Id` (echoed when the client sends a well-formed one). A `500` returns the same value as `error_id`, so an id reported by an application finds the traceback in the server log.
- **JSON logs.** `VOICEBOX_LOG_FORMAT=json` switches the application and uvicorn loggers to one JSON object per line (`ts`, `level`, `logger`, `msg`, `request_id`, `key_id`, and for access lines `client`, `method`, `path`, `status`). Query strings still have media tokens and OAuth codes redacted.
- **Metrics.** `GET /metrics` (admin key) serves Prometheus metrics: HTTP requests and latency by route, queue depth and wait, synthesis duration and characters per engine, time to the first streamed chunk, Whisper/LLM slot waits, model load times, rate-limit rejections, CUDA memory. `VOICEBOX_METRICS_PORT=9464` additionally serves them on a separate unauthenticated port for scrapers that cannot send a bearer; keep that port on a private network.
- **Load test.** `scripts/load_test.py --url ... --key ... --voice ... --model kokoro --concurrency 4 --requests 20` streams through `/v1/audio/speech` and prints time to first byte, total time, realtime factor and the 429 count. Run it once per engine on the target hardware before choosing rate limits. For scale: Kokoro on an Apple M-series CPU serves sentence-length requests with the first byte after about one second and produces roughly six seconds of audio per wall second per request.

## 8. Throughput

One process serves one request at a time per lane. By default there is one lane, so synthesis is strictly serial: the right choice for a single GPU, where two engines would only fight over memory.

- `VOICEBOX_GENERATION_WORKERS=2` splits the queue into a `cpu` lane and a `gpu` lane, each with its own worker. A CPU engine (Kokoro, LuxTTS, and on macOS most engines) then synthesizes while a GPU engine does, so a server that offers a fast preset voice next to a cloned one no longer makes the fast one wait. Jobs in the same lane still run one after another, and two GPU engines never overlap. Requests with a `seed` run exclusively (the seed is process-wide), so seeded traffic briefly pauses the other lane. Apple Silicon (MLX) always stays on one lane.
- `VOICEBOX_MODEL_IDLE_UNLOAD_S=900` unloads engines that finished their last job more than that many seconds ago, and Whisper or the LLM when their slot has been idle as long, so a server with several engines does not keep all of them resident for a request that came once. Preloaded models are never unloaded. The minimum is 30 seconds.
- `POST /models/{name}/unload` answers `409` while that engine has a job queued or running.
- Same-engine concurrency is off by default because the backends share model state. `VOICEBOX_ENGINE_CONCURRENCY=kokoro=2,qwen=2` lets that many jobs of one engine run at once within a lane: the queue still hands out jobs strictly in order, a different engine waits until the lane is empty, and seeded jobs still run alone. Only engines reviewed for it are accepted (`kokoro`, `qwen`, `qwen_custom_voice`, `luxtts`, `tada`; Chatterbox stores the reference voice on the model, so it stays serial), at most 4 each, and Apple Silicon (MLX) ignores the setting. Measure with `scripts/load_test.py` before and after: on a GPU a second job of the same model often adds throughput, on a CPU it usually only shares the cores.

## 9. Backups

Everything lives in the data directory (`/app/data` in the container, the `voicebox-data` volume): `voicebox.db`, `profiles/`, `generations/`, `captures/`, `api_key` and `api_keys.json`. The database runs in WAL mode, so a file copy must include `voicebox.db-wal` and `voicebox.db-shm`, or use `sqlite3 /app/data/voicebox.db ".backup /backup/voicebox.db"` for a consistent snapshot. Keep the data directory on a local disk: SQLite's WAL is not safe on NFS.

Models are cached separately (`huggingface-cache` volume or `VOICEBOX_MODELS_DIR`); they are redownloadable and need no backup. Neither does a replica whose voices come from a seed directory and whose keys come from a mounted file (section 12): everything else it holds is disposable.

## 10. Transport and limits

- Terminate TLS in front of the server: the Caddy overlay (`docker-compose.tls.yml`) does it with automatic certificates. Keys must never travel over plain HTTP outside loopback or a private network.
- Behind your own proxy, set `FORWARDED_ALLOW_IPS` to the proxy's address so per-IP limits see the real client, and disable response buffering for `/generate/stream` and the SSE routes.
- Set `VOICEBOX_ALLOWED_HOSTS` to the public name(s) (`voice.example.com`, `*.internal.example.com`). A browser tricked into resolving an attacker's domain to your server's address then sends that domain as `Host` and is refused with `400`; loopback names, `/health`, `/health/ready` and `/metrics` keep working for the desktop shell, probes and scrapers.
- Per-key rate limits, upload caps and the queue depth are described in [API Keys](/overview/api-keys). Raise a key's limits in `api_keys.json` rather than turning limiting off.

## 11. Upgrading

Pull the new image (or rebuild), then `docker compose up -d`. Schema migrations run at startup and are idempotent. Stop the old container gracefully first (see above) so in-flight generations finish, and take a backup before a major version.

## 12. Voices as configuration

A voice profile travels as a `.voicebox.zip` bundle: the Export button in the UI, `GET /profiles/{id}/export` and `python -m backend.voices export ./seed` all write the same file, and it now carries everything a preset, designed or cloned profile needs (voice type, preset voice, default engine, effects chain, personality, samples). Three ways to get voices onto a server:

- **Seed at boot.** `VOICEBOX_SEED_PROFILES=/seed` imports every bundle in that directory when the server starts. A name that already exists is skipped, so restarts and rolling updates are idempotent; `GET /health/ready` answers `503` until the seed is applied and stays `503` when a bundle is invalid, which is how a broken catalog is caught during a rollout rather than by an application. `python -m backend.voices import ./seed --on-conflict replace` applies a changed bundle in place.
- **Presets need nothing.** `POST /v1/audio/speech` accepts a built-in voice id directly (`af_heart`, `kokoro:af_heart`, `Ryan`), and `GET /v1/voices` lists them next to the profiles.
- **Applications create their own.** `POST /v1/voices` (multipart `name`, `file`, optional `text` transcripts) clones a voice owned by the calling key; it is invisible to other client keys, `DELETE /v1/voices/{voice}` removes it, and the key's `max_voices` limit (default 50) caps the count. Admin keys see and may delete everything. Such voices live in one replica's database, so in a fleet they belong to that replica; catalog voices belong in the seed.

## 13. More than one replica

The speech and transcription routes keep no state between requests, so the way to grow is more identical containers behind the platform's load balancer. A replica needs three inputs: the seed directory above, the hashed keys file (`VOICEBOX_API_KEYS_JSON` pointing at a mounted secret; `VOICEBOX_API_KEY` for the admin key; `VOICEBOX_MEDIA_TOKEN_SECRET` when the browser UI is served through the balancer) and the models on disk (`VOICEBOX_BAKE_MODELS` at build time, or a shared volume filled by `python -m backend.preload` and `HF_HUB_OFFLINE=1`). Probe `/health/ready`, give the platform 90 s to stop a replica, target two concurrent requests per replica and set `VOICEBOX_MAX_QUEUE_DEPTH` a little above that. The [Scaling](/overview/scaling) page has the per-platform settings and `deploy/` in the repository the manifests; `docker-compose.fleet.yml` runs the smallest fleet locally and `scripts/fleet-check.sh` verifies any of them.
